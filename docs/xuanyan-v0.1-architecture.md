# 玄言架构说明

## 1. 文档地位

本文只描述当前实现边界和事实归属。

- 语法与可观察语义以
  [`xuanyan-v0.1-language-reference.md`](xuanyan-v0.1-language-reference.md)
  为唯一事实来源。
- 已完成方案只保留在 Git 历史中，不作为当前实现事实。

## 2. 产品管线

单文件和本地包进入同一条产品管线：

```text
.xy 源码
  -> Lexer / Parser / AST
  -> ModuleLoader / Resolver
  -> 类型与所有权分析
  -> HIR
  -> CFG MIR + Validator
  -> 原生代码生成
  -> 原生 artifact
```

`Compiler` 是统一入口。`检查` 在 MIR 验证后结束；`运行`、`构建` 和 `测试`
只进入原生代码生成，不存在解释器、Rust 源码渲染、后端选择或回退路径。

当前原生后端直接生成 x86_64 Windows PE、Linux ELF 或 macOS Mach-O。生成过程
不启动外部编译器、汇编器或链接器。macOS 当前只形成基础整数、整数结果和布尔
测试闭环，未覆盖的 Darwin 宿主 ABI 统一报告 `NBE001`。

## 3. 原生后端

原生后端只消费已验证 MIR、具体类型、LangItem 和统一宿主 ABI：

- 可达泛型函数、静态协议调用、函数值和闭包按具体实例生成。
- 值、位置、移动、借用、释放和控制流事实来自 MIR，不在后端重复推断语义。
- Windows、Linux 与 macOS 共用实例、值布局和私有调用约定，只在 artifact 格式
  与系统调用边界分开。
- 未覆盖的类型、布局、宿主调用、借用或投影统一报告 `NBE001`。
- 生成的 artifact 不保存 MIR 指令表、字节码、通用动态值、body 注册表、协议
  分发表或通用位置解释器。

入口输出由后端根据 MIR 返回类型和核心 LangItem 生成：

- `空` 成功退出且不写标准输出。
- 其他普通返回值写入标准输出并成功退出。
- `结果<T, E>` 的成功载荷写入标准输出，失败载荷写入标准错误并以状态 1 退出。
- 包测试布尔入口返回真时状态为 0，返回假时由包服务保持既有 `RBE003` 诊断。

小数文本和 Unicode 大小写转换使用随编译器保存的固定 x86_64 位置无关代码块。
仓库中的 Rust 源码只用于维护该代码块；用户执行 `运行`、`构建` 或 `测试` 时不会
启动 `rustc`，该维护源码也不构成第二产品编译管线。

## 4. 事实归属

| 事实 | 唯一所有者 | 下游 |
| --- | --- | --- |
| 源码位置和语法结构 | Lexer / Parser / AST | Resolver、诊断 |
| `FileId` 与原生路径 | ModuleLoader | Resolver、包测试、定义索引 |
| 声明、导入、可见性和引用目标 | Resolver | 类型分析、HIR |
| 类型、值使用方式、协议调用和调用期借用 | 类型与所有权分析 | HIR |
| 已解析身份、类型和控制语义 | HIR | MIR lowering |
| 控制流、Place、移动、借用和释放 | MIR | Validator、原生后端 |
| 核心类型、协议和入口身份 | Resolver LangItem | HIR、MIR、原生后端 |
| 可达具体实例和实例调用边 | 原生后端实例收集 | 原生后端 |
| 宿主函数身份和 ABI | 核心库宿主注册表 | Resolver、MIR、原生后端 |
| 包清单、包根和本地依赖图 | 本地包服务 | Compiler、ModuleLoader |
| 诊断代码、位置、正文和附件 | 核心诊断模型 | CLI、LSP |
| JSON-RPC、URI 和 UTF-16 位置 | `xuanyan-lsp` | LSP 客户端 |

Resolver 用 `DefId` 连接声明与引用。HIR 不执行程序。Validator 在代码生成前检查
MIR 的控制流、位置、类型形状和数据流不变量。后端不得通过中文名称、宿主函数名
或参数形状建立第二份语义判断。

## 5. 核心库、标准库与宿主 ABI

`corelib` 声明 `可选<T>`、`结果<T, E>` 和基础协议。Resolver 把编译器必须识别
的声明登记为 LangItem，下游不依赖中文名称字符串决定语义。

`stdlib` 是普通玄言本地包。普通组合能力优先使用 `.xy` 源码；只有需要宿主资源、
平台系统调用或固定运行时布局的操作才登记宿主函数。宿主登记集中在
`core_library.rs` 与 `core_library/abi.rs`，不维护第二份公开名称映射。

宿主资源继续服从普通所有权和 MIR `Drop`：

- 文件、目录、环境、进程参数、标准输入输出和路径操作直接进入平台宿主边界。
- TCP 监听器与连接、线程、同步通道和原子整数使用固定宿主载体与 ABI。
- 字符串和拥有列表使用具体布局；借用只传递已有存储位置，不转移所有权。
- `可选`、`结果` 和具体 ADT 只按已验证类型生成，不使用运行时类型标签。

语言侧公开名称、所有权、副作用和错误语义由语言参考定义，后端实现细节不构成
新的语言规则。

## 6. 本地包

包服务只支持本地工作流：

- `xuan.toml` 指定包入口。
- 依赖只接受显式本地路径；相对路径以声明包为基准，完整绝对路径按当前宿主解释。
- 包服务不展开环境变量，也不搜索隐式标准库或全局包目录。
- 包源码必须位于对应包根内。
- 根包与本地依赖闭包形成唯一的 `LocalPackageGraph`。
- ModuleLoader 直接消费包图，不重新解析依赖关系。
- 源码只按导入可达关系加载；包节点与依赖边保持确定顺序。
- LSP 打开的源码由规范路径全文覆盖，其他源码仍从磁盘读取。

`测试` 递归发现 `tests/**/*.xy` 中无参数公开函数。返回类型不是 `布尔` 时，包服务
在代码生成前报告 `PKG009`；合法测试逐项作为精确原生入口构建和执行。首个返回假
或执行失败的测试报告函数名与包根相对路径，不生成汇总入口或测试 runner。

远程 registry、发布、搜索和网络依赖解析不属于本地包服务。

## 7. CLI 与 LSP

CLI 只负责命令参数、输出通道、诊断文本和退出状态：

- `检查`、`运行`、`构建`、`测试`、`格式化` 是唯一公开命令。
- 文件与输出路径保持 `OsString` / `PathBuf`。
- 命令名、入口函数名和玄言程序参数在边界显式验证 UTF-8。
- `运行` 的第一个 `--` 是入口参数与程序参数的唯一分隔符。
- 进程标准输出、标准错误和非零状态通过统一执行边界处理。

`xuanyan-lsp` 是独立 crate。它复用 Compiler 的加载、Resolver、类型分析和诊断
事实，只负责 LSP 协议、URI 与 UTF-16 位置转换，不建立第二套解析或语义模型。

## 8. 平台能力与门禁

所有目标复用同一 Parser、Resolver、HIR、MIR、类型系统和语言参考。平台差异只允许
存在于原生产物格式、调用约定、宿主 ABI、应用壳和验证证据中。`检查` 是平台无关的；
程序通过 `检查` 不代表每个目标后端都已经覆盖它使用的全部类型和宿主能力。

平台能力分为三层：

- 语言核心：语法、类型、泛型、所有权、控制流和 MIR 语义，各目标不得另行定义。
- 可移植库能力：公开语义可以跨目标保持一致的普通 `.xy` 实现和宿主入口；平台实现
  可以不同，但语言参考规定的可观察结果不得改变。
- 平台专属能力：桌面窗口、移动生命周期和沙箱等依赖目标环境的宿主入口，只承诺
  明确列出的平台和边界。

当前支持等级：

| 等级 | 平台 | 当前承诺 |
| --- | --- | --- |
| 完整支持 | Windows x86_64、Linux x86_64 | 公开工具链、完整原生后端、语言参考接受程序、标准库、包工作流、CLI、LSP、离线安装和持续真实门禁 |
| 技术预览 | Android arm64-v8a、HarmonyOS NEXT arm64-v8a | Windows/Linux 宿主直接生成固定 AArch64 ELF 共享库，覆盖已发布移动能力并通过对应应用壳和真机门禁 |
| 预留，未发布 | macOS x86_64、iOS | macOS 只保留 Mach-O 结构和基础产物测试，iOS 尚未接入；都不属于当前发布承诺或验收门禁 |

目标构建必须按以下顺序处理差异：

- 目标后端未覆盖的类型、布局、宿主调用、借用或投影统一报告 `NBE001`。
- 无效或未公开的 CLI 平台名称报告 `CLI004`。
- 已接入能力因权限、文件、网络、证书或系统运行库失败时，执行宿主函数既有的普通
  返回值或 `结果` 错误语义，不改报 `NBE001`。
- 不支持的能力不得成为空操作、伪造成功，也不得恢复解释器、Rust 源码生成或第二
  编译管线。

宿主能力继续以统一 `HostFunctionId` 登记为事实来源。每个目标后端要么实现该身份，
要么在构建时拒绝；诊断中的玄言公开名称必须取自同一宿主登记，不维护第二份名称或
逐函数平台矩阵。发布文档只按能力领域说明覆盖范围。

当前不提供条件编译语法、目标查询、用户构建标签或任意 target triple。真实包确实
需要在同一公开接口下维护互斥平台实现时，优先评估固定平台文件选择，并作为独立语言
工作包定义选择、冲突和缺失规则；在此之前，文件名和目录名不具有条件编译语义。

快速门禁覆盖核心单元、规范、二进制宿主 ABI、字段可见性和 LSP 协议边界。Windows
与 Linux 还必须运行完整原生后端、包工作流、CLI 和本地安装门禁；Android 与
HarmonyOS NEXT 相关工作必须运行对应结构和真机门禁。x86_64 macOS 只运行 Mach-O
结构和当前基础闭环的定向门禁，不得写成已经通过 macOS 原生验证。完整命令见
[`CONTRIBUTING.md`](../CONTRIBUTING.md)。公开仓库只运行
[公开源码边界门禁](../.github/workflows/public-safety.yml)；完整产品门禁在私有源码树中执行。

每个工作包完成后都必须在 Windows 和 WSL2/Linux 验证、提交并做方向检查。移动平台
工作包还必须提供对应设备证据。macOS 基础后端不包含跨编译抽象、兼容层或回退开关，
后续 Darwin 宿主 ABI 与 AArch64 机器码只能依据外部可复现问题分别选择工作包。
